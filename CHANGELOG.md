# Changelog

## Unreleased

- **Every command checks what it needs before it starts.** A new checker, `scripts/check-prereqs`, holds one registry of the tools the plugin uses (`git`, `python3`, `rsync`, `gitleaks`, `typos`) with install steps for macOS, Debian or Ubuntu and Windows. Each command that needs one runs it first (pre-approved in its `allowed-tools`, so no prompt). A missing required tool stops the command before it changes anything, with the install message and `Next: install what is missing, then run /spike-loop:<command> again`. A missing optional tool skips only the step that uses it, and says so. Agents run the check themselves only when called directly. Before this, a machine without `git` got a plausible answer about the wrong repo root, because the root finder read the failure as "not a git repository". See `docs/prerequisites.md`.
- **`python3` is now optional for `/spike-loop:poc-research`:** without it, research uses public sources only and says so. `rsync` is recorded as required by the packager's clean-clone test.
- **`/spike-loop:poc-log` computes its time check with a script.** `skills/poc-log/scripts/time_check.py` works out elapsed time, the entry count (the log's template line is never counted, a known bug before) and whether the timebox is over, and the over-timebox `Next:` line keys on its result. Without `python3` the entry is still written and the time check is reported as not run; the time is never estimated. Known Haiku limit: the line is copied with its numbers, but not always word for word (17 of 20 headless runs exactly; one in 20 gave no numbers). Nothing reads the line, so its values are what is checked.
- Checked headless on Claude Code 2.1.325: probes for `allowed-tools` in a plugin skill (quoted, unquoted, a path with a space), a forked agent, and hidden tools; then 89 eval runs, after which the fixes above were made and the changed cases re-run. Not checked: an installed (marketplace) plugin, an interactive session, Windows.
- **Evals Phase 2 (in progress).** A grader library for the eval harness (`evals/harness/graders.py`), 7 more `poc-log` cases and 26 cases for `poc-start`, `poc-checkpoint`, `poc-verify` and `poc-sources`, each checked against a hand-made correct result and a planted defect before any live run. Cases can hide tools from `PATH` (`hide_tools`). Smoke runs only so far. See `evals/README.md`.

## 0.3.1

- **`/spike-loop:poc-build` no longer guesses which of your commits the worktree has.** The 0.3.0 text said the worktree always branches from the remote default branch, so unpushed commits are never in it. In headless runs that was false in two cases: with no remote, and with `worktree.baseRef` set to `"head"`, the worktree started from your current commit. The command now runs `git log --oneline HEAD --not <branch>` after the build and names the commits on your current branch that the worktree lacks, or says it holds them all. Uncommitted work is never in the worktree. Checked headless, one run each, on Claude Code 2.1.325: no remote, a remote with `worktree.baseRef: "head"`, and a remote without it.
- **The implementer agent commits its change in its worktree** when the done condition is met, unless the brief says not to, and never in the main checkout. `poc-build` already asked for this in its brief; the rule is now in the agent too.
- Checked once interactively as well (Claude Code 2.1.325, plugin loaded with `--plugin-dir`, a repo with no remote): the worktree was made, the change committed on its branch and the main tree left alone, as in the headless runs. An installed plugin was not checked.

## 0.3.0

- **A fresh session can pick a PoC up from disk.** `/spike-loop:poc-checkpoint` now ends its outcome entry in `LOG.md` with one `State:` line: branch, commit, uncommitted paths (a count and up to five names), unmerged `poc-build` worktree branches, what is waiting on you, and how to resume. The values come from read-only git calls (`git --no-optional-locks`), never from memory. Worktree paths, file contents and environment values are never written.
- **`/clear` only after the state is on disk.** The checkpoint reads the entry back before it prints `Next:`, and only then suggests `/clear`, followed by `/spike-loop:poc-help` in the fresh session. If the write or the read-back fails, it says so and suggests no `/clear`. A skill cannot clear context: you still type `/clear`.
- **New outcome `pause`.** `/spike-loop:poc-checkpoint pause [topic]` stops mid-step with no loop decision, for example during spec or plan work. With a topic it also writes `poc-spec/handoffs/<date>-<topic>.md` (at most 40 lines, never overwriting: `-2`, `-3`) and the State's resume field names it. Topics must be `[a-z0-9-]+`. A PoC in the older root layout gets the entry and State but no hand-off file. `pause` is accepted wherever an outcome is listed.
- **`/spike-loop:poc-help` checks the State.** It reads the State only from the last log entry, compares it with the repo (branch, a reset or new commits outside the docs files, uncommitted paths), and prints the resume step, or `State is from <date>; it may be stale: <what differs>` and a checkpoint to record it again. Changes to `LOG.md`, `SUMMARY.md` and `.claude/` never count. A State with a later log entry is "State unknown". No `Next:` line in `poc-help` or `poc-log` names `/clear` any more: iterate, pivot and pause point at the checkpoint.
- **Known limit: the staleness check runs only when you type `/spike-loop:poc-help`.** In headless probes, a fresh session asked to "continue" read the log and acted on the resume step directly, and the model cannot run `poc-help` itself. A `SessionStart` hook that runs the check is possible future work (`docs/handoff/spec.md`, "Future work").
- **Known gap: the packager does not warn about hand-off files.** Its docs-folder warning checks `poc-spec/POC.md` and `poc-spec/LOG.md` by name, so a tracked file under `poc-spec/handoffs/` can travel with no warning when those two are ignored. Keep customer and deal names out of topics and hand-offs in a public repo.
- What was checked. A free script, `docs/handoff/tools/check_git_rules.py`, runs the git rules on scratch repos (older layout, no commits, not a repo, detached HEAD, linked and detached worktrees, a reset, unusual file names) and a mutation harness shows each check can fail. 26 new text tests parse the skills against the spec. Seven headless probes, one run each on Claude Code 2.1.325 (`docs/handoff/findings.md`): a fresh session read the log tail and used the State, followed a resume pointer to a hand-off file, and `/clear` and plugin `SessionStart` hooks behaved as described there. The real `poc-checkpoint` and `poc-help` were then run headless on 15 scratch-repo cases (17 runs, one each): iterate with an uncommitted file and an unmerged worktree, fresh and stale States (a code commit, a detached HEAD, a reset, a new file in an older-layout PoC), docs-only and `SUMMARY.md` changes that must not count, a later entry, an old log, no commits, not a repo, `pause` with a taken name and then a fresh session, a bad topic, and a failed write. Two problems were found and fixed: the resume field could name `poc-help` itself, and the grader was too strict about wording. One run each, not a pass rate. Not checked: an interactive session, an installed (not `--plugin-dir`) plugin, and PoCs wired before 0.2.0.

## 0.2.1

- **`/spike-loop:poc-build` now runs the implementer in a worktree, as documented.** Until now the command was a `context: fork` skill, and in a headless test on Claude Code 2.1.325 that ran the implementer in your main working tree: the agent's `isolation: worktree` was not applied, so edits landed in your tree and no worktree was made. The command now calls the agent through the Agent tool, which did create a worktree in the same test. The Claude Code docs do not say whether a forked skill honours `isolation`, so this is based on that one observation, not on the docs. Not checked in an interactive session.
- **What changes for you.** The change is on the worktree's branch, not in your tree. The command reports the worktree path and branch, says whether the change is committed or only uncommitted in the worktree, and its `Next:` line is `git merge <branch>` (or a commit step first) then `/spike-loop:poc-verify`. It never merges for you. Per the Claude Code docs the worktree starts from the remote default branch, so unpushed commits and uncommitted work are not in it: to include local work, commit it and set `worktree.baseRef` to `"head"`. A repo with no remote was not checked.
- Three tests: `poc-build` is not a fork and calls the agent through the Agent tool, it says where the change is and does not merge, and no forked skill names an agent that sets `isolation`.

## 0.2.0

- **New layout.** `/spike-loop:poc-start` now writes `poc-spec/POC.md` and `poc-spec/LOG.md` (and `verify.sh` at the repo root), and appends a `CLAUDE.md` section that points at them. One folder holds the working documents, so it can be left out of a public repo or a customer hand-off. `SUMMARY.md`, `README.md`, `CLAUDE.md`, `verify.sh` and `.env.example` stay at the repo root.
- **Older PoCs keep working.** A PoC with `POC.md` and `LOG.md` at the repo root is read as it is. Nothing is moved for you. To move one: `mkdir poc-spec && git mv POC.md LOG.md poc-spec/` (use `mv` if they are untracked), then update the paths in the `CLAUDE.md` section. If both layouts are present, or only one file was moved, most commands stop, name the files and ask which to keep (`poc-research` answers anyway and says so in its Next line). `/spike-loop:poc-help` prints this as a one-line note when it finds the older layout.
- **Every path is relative to the repo root.** The skills and agents find the root with `git -C <path> rev-parse --show-toplevel`, run shell commands as `cd "<root>" && ...`, use `git -C` for git, and give file tools full paths, so a command is designed to behave the same from a subdirectory. It needs the session to be allowed to use the repo root. If it is refused (for example `cd ... was blocked`) the command says so and does not work around it: start the session at the repo root, or run `/add-dir` with the root.
- **Expect more approval prompts in a session started below the repo root.** Each part of a compound command needs its own approval, and a `cd` outside the session's directories can be refused. Headless runs showed this. Whether an interactive session prompts for each part was not measured.
- **`poc-start` checks before it writes.** It asks if the session directory is not the repo root, if this is a linked worktree (a gitignored `poc-spec/` would be missing from the other worktrees), or if the repo sits inside another repository. It stops in a bare repository. It never overwrites `poc-spec/POC.md`, `poc-spec/LOG.md`, `verify.sh` or an older root `POC.md` or `LOG.md`. The public-repo notice now names `poc-spec/` and does not edit `.gitignore`.
- **The packager warns when `poc-spec/` would travel.** If the docs folder is tracked, or untracked and not ignored, and the PoC is public or tied to a deal, the packager adds a line under Open gaps: `LOG.md` can hold customer names, add the folder to `.gitignore` and untrack it before sharing, anything already pushed stays in history. It reports only and never edits `.gitignore` or runs `git rm`. `/spike-loop:poc-harden` lean path now shows the packager's report, so the warning reaches you.
- **If you ran `/spike-loop:poc-sources`,** run `/spike-loop:poc-sources refresh` to regenerate your `researcher-internal` agent with the new rules. The old copy keeps working as before.
- Checked by hand: the real commands were run headless on 22 scratch repos (a new PoC, the older layout, both layouts, a partial move and none, from the repo root and from a subdirectory, in a bare repository, a nested repository and a linked worktree, and five packager warning cases) on Claude Code 2.1.325, one run each. All behaved as described above, after one fix: a `poc-log` run below the repo root was refused for a check that needed no `cd`. This is one run per case, not a measured pass rate. `poc-checkpoint`, `poc-harden`, `poc-review`, `poc-research`, `poc-build` and `poc-debug` were not run on the new layout, and a model-run eval suite is a follow-up. The packager's clean-clone test cannot run in a session whose permissions exclude a temp directory outside the repo: it says so and the README run steps are then checked in the working tree only.
- Twelve text tests check that every skill and agent carries the two rules word for word, that no skill hard-codes a root document path or a vague "current directory", and that the packager warning and the `poc-start` wording are present. Windows is untested: the shell snippets assume a POSIX shell.

## 0.1.2

- New `/spike-loop:poc-help`: prints the command table, explains one command (`/spike-loop:poc-help verify`), and reads `POC.md` and `LOG.md` to say where the PoC stands and what to run next. It writes nothing.
- Every command now ends with one line starting `Next:` that names the next command, chosen by the outcome: verify on a pass or fail, review with or without blocking findings, harden when blocked or complete, log by the entry's Decision, and so on. The forked commands (`poc-build`, `poc-verify`, `poc-debug`, `poc-review`, `poc-package`) add it in the skill, not in the agent, so the agents' output contracts used by `poc-harden` are unchanged.
- A test checks that every command has a `Next:` rule, that `poc-help` lists every command, and that the README lists them too.

## 0.1.1

- Classifier: `edit`, `append`, `insert`, `replace`, `save`, `push`, `submit`, `import`, `attach`, `tag`, `store`, `modify` and similar verbs now make a tool write-class, so compound names such as `search_and_replace` are no longer offered as read.
- `render-agent` refuses a base agent with no `tools:` line, `init-sources` and `render-agent` accept a bare relative `--out`, and `status` no longer reads stdin.
- The packager's clean-clone test copies the working tree, so the files it just wrote are part of the test.
- `POC.md` `Started:` now includes the time, and `poc-log` and `poc-checkpoint` measure wall-clock time against the timebox.
- Reworded the read-only and no-external-access claims, and documented the limits in `docs/updating-sources.md`.
- Install, update and uninstall steps in the README, a plugin icon, and manifest metadata.
