# Plugin findings from the evals work

Defects and doubtful claims found while building the evals. They are logged here and fixed on a separate branch, so a change in eval scores is never confused with a change to the evals.

## F1: `/spike-loop:poc-build` does not run in a worktree (observed, headless only so far)

- **Claim:** `README.md` ("in a git worktree"), `docs/workflow.md` ("own worktree") and `skills/poc-build/SKILL.md` ("in an isolated worktree") say the implementer runs isolated. `agents/implementer.md:7` sets `isolation: worktree`.
- **Observed:** Claude Code 2.1.325, headless, 2026-11-25, on a fixture git repo. Running `/spike-loop:poc-build <task> | done when <condition>` (a `context: fork` skill with `agent: spike-loop:implementer`) made the implementer run in the main working tree. Its first command printed the fixture's own root from `git rev-parse --show-toplevel`, `hello.txt` appeared untracked in the main tree, and `git worktree list` showed no extra worktree.
- **Contrast:** calling the same agent through the Agent tool (`subagent_type: spike-loop:implementer`) did create a worktree at `<repo>/.claude/worktrees/agent-<id>`, on branch `worktree-agent-<id>`, with the change inside it and nothing in the main tree except an untracked `.claude/`.
- **Not known:** whether an interactive session behaves the same as a headless one. Not checked against the docs yet.
- **Why it matters:** a user who runs `/poc-build` expecting isolation gets edits in their working tree. This is a claim about the product that is not true in the tested path.
- **Fixed in 0.2.1 (branch `fix-poc-build-worktree`, 2026-11-26):** `poc-build` is no longer a fork. It calls `spike-loop:implementer` through the Agent tool, reports the worktree path and branch, and does not merge. The Claude Code docs (skills, sub-agents, worktrees pages, read 2026-11-26 through a summarising fetch) are silent on whether a forked skill applies the agent's `isolation`, and give a skill no way to force a worktree, so the fix rests on the observation above. Verified after the change with one headless run of the real skill on a scratch repo (Claude Code 2.1.325): a worktree and branch were created, the commit was inside it, and the main tree had only an untracked `.claude/`. Side effects: the docs say the worktree starts from `origin/<default>`, not your current branch (so unpushed commits and uncommitted work are absent), and the implementer committed in its worktree in this run but left the file untracked in the earlier spike run, so the skill now tells it to commit and checks the result. Still not checked: an interactive session.
- **Second check after review feedback (2026-11-26, same version):** on a scratch repo with a remote, one unpushed local commit and one uncommitted file, the worktree held only the pushed files, so the base is `origin/<default>` as documented. The brief the skill sent named no main checkout and said to commit in the worktree, the main tree was untouched, and the skill reported the change as uncommitted and the chunk as failed when the agent could not finish (its Bash grants in that headless test were too narrow). One run, headless.
- **Follow-ups (2026-11-27, Claude Code 2.1.325, headless, one run each, `docs/evals/tools/f1_followups.py`):** three scratch repos, each with a first commit A, a local commit B and an untracked `dirty.txt`, running `/spike-loop:poc-build` on a one-file task.
  - R1, no remote: the worktree started from B (the local HEAD). R2, a remote with B unpushed and `worktree.baseRef: "head"`: also from B, so the setting works as documented. R3, the same remote with no setting (the control): from A, so B was missing.
  - In every run the implementer committed on its `worktree-agent-<id>` branch, the main tree gained only an untracked `.claude/`, and `dirty.txt` was not in the worktree.
  - **Defect found:** the 0.3.0 skill stated the base as fixed ("branches from `origin/<default>`, so unpushed commits are not in it"), which was false in R1 and R2. Fixed in 0.3.1: the skill runs `git -C "<main root>" log --oneline HEAD --not <branch>` and names what the worktree lacks. Re-run of all three: each report was true (R1, R2 "holds all your current commits", R3 names commit B as missing).
  - `agents/implementer.md` now carries the commit rule itself (commit in the worktree when the done condition is met, unless the brief says not to, never in the main checkout), so it holds when the agent is called directly.
  - **Interactive check (2026-11-27, run by the maintainer, Claude Code 2.1.325, `--plugin-dir`):** a fresh repo with one commit and no remote, `/spike-loop:poc-build Create hello.txt containing hi | done when hello.txt exists and contains hi`. Result: a second worktree at `.claude/worktrees/agent-<id>` on `worktree-agent-<id>`, the change committed there, `hello.txt` absent from the main tree, and the report named the branch and the merge step. Same behaviour as headless. One run. An installed (not `--plugin-dir`) plugin is still unchecked.
- **Possible fixes considered:** have `poc-build` call the agent through the Agent tool instead of `context: fork`, or change the claims. Confirm against the Claude Code docs for `isolation` and `context: fork` first.

## F2: `/spike-loop:poc-log` paraphrases the time-check line (observed 2026-11-27, 1 run of 18; wording changed on the `evals-phase-2` branch, not shown to help)

`poc-log` step 4 says to print one line, `Elapsed <x> of <timebox>, <n> entries.` In one of three runs of `poc-log/within-timebox` (Claude Code 2.1.325, Haiku), the run printed `Elapsed 2 days (since 2026-11-25 18:30), well inside the timebox of 100000 hours, and 2 entries.` The facts were right and the entry was correct, but the fixed line was rewritten, so anything that reads that line (the case grader, a user scanning for it) misses it. The other 17 Phase 2 `poc-log` runs printed the line as written. This is the known pattern of Haiku paraphrasing fixed text (see `docs/handoff/findings.md`). The line was already in a code span in the skill.

- **Fix:** step 4 now says "Print this line exactly, with only the three values filled in: `Elapsed <x> of <timebox>, <n> entries.` Put any comment on the next line, never inside it." Pinned by `tests/test_skills_contract.py`.
- **Re-run (2026-11-27, Claude Code 2.1.325, Haiku):** `within-timebox` 10 times and every other `poc-log` case once, 21 runs, about $0.08. The line's wording was right in all 21 runs (the elapsed value is written in several forms, such as `47h 15m`, `47h15m`, `47:17` and `47 hours 16 minutes`, which the step allows). In one run (`fresh-log`) the comment followed on the same line, after the full stop. The case graders now require the line to end after `entries.`, so that run counts as a fail.
- **Still slips:** in the F3 re-run, 2 of 18 runs broke the line rule, one with a comment on the same line and one rewording it (`Elapsed 47.4 hours of the 100000-hour timebox, 2 entries.`). Across both re-runs, 3 of 39 runs. That is no better than the 1 in 18 before the change (and the graders now also count a same-line comment, which they did not before), so the change is not shown to help. The rule is not reliable on Haiku.
- **Moved to a script (branch `prereqs`):** `skills/poc-log/scripts/time_check.py` now computes the line, the entry count and whether the timebox is over, and the skill copies its first line (`docs/prereqs/spec.md`). Whether copying holds better than building the line is measured in that branch's re-run.
- **Bad case found in the re-run:** `within-timebox` graded "not over the timebox" by searching for words such as "exceed", and "Timebox is far from exceeded" matched. It now checks that the reply does not list the outcomes to decide between, which is what the skill prints when the timebox is over.

## F3: `/spike-loop:poc-log` points at `poc-verify` when the timebox is over (observed 2026-11-27, 1 run of 4; fixed on the `evals-phase-2` branch)

`poc-log` step 5: with Decision `none yet`, "keep building and run `/spike-loop:poc-verify` ... (if over the timebox, decide now with `/spike-loop:poc-checkpoint <iterate | pivot | harden | stop | pause>`)". In one of four runs of `poc-log/timebox-exceeded` (Claude Code 2.1.325, Haiku) the reply said the timebox was over and listed the outcomes, but the `Next:` line was `/spike-loop:poc-verify`. The other three runs pointed at the checkpoint. The over-timebox rule was a parenthesis inside the `none yet` rule.

- **Fix:** step 5 now starts with its own rule: "First, if the time check found the timebox exceeded and the Decision is `none yet`, the line is `Next: /spike-loop:poc-checkpoint <iterate | pivot | harden | stop | pause>` to decide now, never `/spike-loop:poc-verify`." Pinned by `tests/test_skills_contract.py`. The skills mutation harness (`docs/handoff/tools/mutate.py`) still gives 50 rows, 0 wrong.
- **Re-run (2026-11-27, Claude Code 2.1.325, Haiku), 18 runs, $0.067:** `timebox-exceeded` 10 times, `within-timebox` 5 times, and `fresh-log`, `earlier-entries` and `started-no-time` (all over the timebox) once each. The `Next:` line was right in all 18: the checkpoint in the 13 over-timebox runs, `poc-verify` in the 5 within-timebox runs.
- **Bad case found in the re-run:** `timebox-exceeded` checked "says it is over" with a word list, and "was passed long ago" was not in it. It now checks that the reply offers the outcomes (`iterate`, `pivot`, `harden`, separated by commas or `|`), the same signal `within-timebox` checks is absent.
- **Moved to a script (branch `prereqs`):** the over-timebox decision now comes from the time check script's `timebox: over` line, not the model's reading of the elapsed time.
