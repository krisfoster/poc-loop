---
name: poc-build
description: Runs the implementer agent in an isolated git worktree on one bounded chunk of an approved plan. Use only when the user types /poc-build with the task and a one-sentence done condition.
disable-model-invocation: true
argument-hint: "<task> | done when <condition>"
allowed-tools:
  - Bash(sh ${CLAUDE_PLUGIN_ROOT}/scripts/check-prereqs *)
  - Bash(sh "${CLAUDE_PLUGIN_ROOT}/scripts/check-prereqs" *)
---
Implement this chunk: "$ARGUMENTS".

**Prerequisites.** Before anything else, run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/check-prereqs" poc-build git` and read its output. If the last line is `prereqs: missing ...`, print each `MISSING:` line as it is, change nothing, and end with `Next: install what is missing, then run /spike-loop:poc-build again`. Print any `skipped:` line and leave out the step that needs that tool. If the check cannot run (refused, not found, or no POSIX shell), say so in one line and continue: a command that needs a missing tool will fail with its own error. This check covers any agent this command starts: when you brief an agent, say "prerequisites checked".

**Paths.** Every path in this command is relative to the repo root. Find the root with `git -C "<target>" rev-parse --show-toplevel`, where `<target>` is the project path given in the arguments if this command takes one and one is given, otherwise the directory the session was started in (an agent uses the repo root named in its brief, and outside a git repository the root is `<target>`). The shell can be reset to the start directory between calls, and is in an agent, so run a command that needs the working directory (it uses a relative path or runs a script there) as `cd "<root>" && <command>`, run git as `git -C "<root>" <subcommand>`, and run any other command as it is (such as `date`, a script by its absolute path, or `chmod` or `tail` given a `<root>/<path>`), unless a step names another directory. File tools (Read, Write, Edit, Glob, Grep) resolve a relative path against the start directory, so give them `<root>/<path>` in full, and use them to check, read and list files. If a shell command or tool is refused (for example `cd ... was blocked`) because the repo root is outside the directories this session may use, do not work around it: say so (an agent reports it and stops), and tell the user to start the session at the repo root or run `/add-dir "<root>"`. A relative project path in the arguments is relative to the directory the session was started in, only to find the root. Everything else is relative to the root.

File paths named in the task are relative to the repo root.

1. **Check the arguments.** They must hold a task and a one-sentence done condition. If either is missing, reply only with `NEEDS INPUT: give me the task and a one-sentence done condition`, then the `Next:` line below.
2. **Call the agent.** Call the `spike-loop:implementer` agent once through the Agent tool (do not run it as a fork of this skill: a forked skill ran it in the main working tree, so the agent's `isolation: worktree` was not applied). The agent has no conversation history, so the brief holds the task, the done condition, and the verification command if the user gave one. Do not put the main checkout's path in the brief. Say instead that its repo root is the root of the git worktree it starts in, that it must not read or edit the main checkout, and that it should commit its change in the worktree when the done condition is met. Tell it not to push or open a pull request.
3. **Report.** Show the agent's report as returned, then say where the change is: the worktree path and branch from the Agent tool result, or that no worktree was reported. Run `git -C "<worktree path>" status --porcelain` and `git -C "<main root>" log --oneline <branch> --not HEAD`, and say whether the change is committed on the branch, uncommitted in the worktree, or both. Then check what the worktree is missing instead of assuming it: run `git -C "<main root>" log --oneline HEAD --not <branch>` and name any commits it prints as on your current branch but not in the worktree. If it prints nothing, say the worktree holds all your current commits. Uncommitted work in the main checkout is never in the worktree. For why: the worktree starts from the remote default branch (`origin/<default>`) when there is a remote, with no remote it starts from your current commit, and `worktree.baseRef` set to `"head"` makes it start from your current commit too. The change stays in the worktree until the user brings it over. Do not merge, cherry-pick or copy it, and do not remove the worktree.

End with one line starting `Next:`. If the change is committed: `git merge <branch>` and then `/spike-loop:poc-verify` to check the chunk (on a feature branch that merge also brings in the default branch's newer commits, so `git cherry-pick <commit>` is the narrower choice). If it is only uncommitted in the worktree: first `git -C "<worktree path>" add -A` and `git -C "<worktree path>" commit -m "<message>"`, then the same. After a `NEEDS INPUT` reply: `/spike-loop:poc-build <task> | done when <condition>` with the missing part.
