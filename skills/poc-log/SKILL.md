# poc-log

Entry text from the user: "$ARGUMENTS". Never use em dashes.

**Prerequisites.** Before anything else, run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/check-prereqs" poc-log git python3:optional` as a command on its own, never joined to another with `;` or `&&`, and read its output. If the last line is `prereqs: missing ...`, print each `MISSING:` line as it is, change nothing, and end with `Next: install what is missing, then run /spike-loop:poc-log again`. Print any `skipped:` line and leave out the step that needs that tool. If the check cannot run (refused, not found, or no POSIX shell), say so in one line and continue: a command that needs a missing tool will fail with its own error. This check covers any agent this command starts: when you brief an agent, say "prerequisites checked".

**Paths.** Every path in this command is relative to the repo root. Find the root with `git -C "<target>" rev-parse --show-toplevel`, where `<target>` is the project path given in the arguments if this command takes one and one is given, otherwise the directory the session was started in (an agent uses the repo root named in its brief, and outside a git repository the root is `<target>`). The shell can be reset to the start directory between calls, and is in an agent, so run a command that needs the working directory (it uses a relative path or runs a script there) as `cd "<root>" && <command>`, run git as `git -C "<root>" <subcommand>`, and run any other command as it is (such as `date`, a script by its absolute path, or `chmod` or `tail` given a `<root>/<path>`), unless a step names another directory. File tools (Read, Write, Edit, Glob, Grep) resolve a relative path against the start directory, so give them `<root>/<path>` in full, and use them to check, read and list files. If a shell command or tool is refused (for example `cd ... was blocked`) because the repo root is outside the directories this session may use, do not work around it: say so (an agent reports it and stops), and tell the user to start the session at the repo root or run `/add-dir "<root>"`. A relative project path in the arguments is relative to the directory the session was started in, only to find the root. Everything else is relative to the root.

**Docs folder.** Check these four paths, relative to the repo root, by reading each with the Read tool (it needs no `cd`, a missing file is just an error, and Glob can skip gitignored files, which `poc-spec/` often is): `poc-spec/POC.md`, `poc-spec/LOG.md`, `POC.md`, `LOG.md`. If files exist only under `poc-spec/`, the docs folder `<docs>` is `poc-spec`. If they exist only at the root, `<docs>` is `.` (an older PoC, use it as is). If files exist in both places, stop, say the PoC is half-migrated, name the files, and ask which to keep (an agent reports this and stops). If none exist, follow the command's own step. `<docs>/POC.md` means `poc-spec/POC.md` or `POC.md`, and likewise `<docs>/LOG.md`.

1. Resolve the docs folder by the docs-folder rule above. If `<docs>/POC.md` or `<docs>/LOG.md` is missing, say to run `/poc-start` and stop, ending with `Next: /spike-loop:poc-start`. If the rule stops on a half-migrated PoC, end with `Next:` naming the fix: keep one layout, then run `/spike-loop:poc-log` again.
2. Build the entry in the format at the top of `<docs>/LOG.md` (Tried, Learned, Dead ends, Decision, Next question, Later). The Decision is one of iterate, pivot, harden, stop, pause or `none yet`. Use the user's text. If it is empty, draft it from this conversation in 2 to 5 lines. Use `none yet` for Decision unless one was stated. Never write a `State:` line: only `/spike-loop:poc-checkpoint` records the state. Use `date '+%Y-%m-%d %H:%M'` for the timestamp.
3. Show the entry, then append it to the end of `<docs>/LOG.md` with the Edit tool. Never edit or reorder earlier entries.
4. Time check: if the prerequisites check skipped `python3`, do not run the script: print the checker's `skipped:` line as it is, then `Time check: not run (python3 skipped)`. Otherwise, after the entry is in the file, run exactly `python3 "${CLAUDE_SKILL_DIR}/scripts/time_check.py" --root "<root>" --docs <docs>` as a command on its own: no `cd` in front, no extra flags, nothing joined to it (it takes the root as an argument). It reads `Started:` and `Timebox` from `<docs>/POC.md` and counts the dated entries in `<docs>/LOG.md`. Print its first line exactly as the script printed it, on a line of its own, and put any comment on the next line, never inside it. If its second line is `timebox: over`, say so plainly and suggest deciding: iterate, pivot, harden, stop or pause. It is a soft limit, so do not nag. If the script printed `time check: <reason>` or could not run (refused, `python3` skipped, any error), print `Time check: not run (<reason>)` and nothing else about time: never work out elapsed time or count entries yourself. Never write the time line or the reason into `<docs>/LOG.md`.
5. End with one line starting `Next:`. First, if the time check printed `timebox: over` and the Decision is `none yet`, the line is `Next: /spike-loop:poc-checkpoint <iterate | pivot | harden | stop | pause>` to decide now, never `/spike-loop:poc-verify`. Otherwise choose by the entry's Decision. `none yet`: keep building and run `/spike-loop:poc-verify` when there is something to check. `iterate`: `/spike-loop:poc-checkpoint iterate`. `pivot`: `/spike-loop:poc-checkpoint pivot`. `pause`: `/spike-loop:poc-checkpoint pause`. Each records the state before the fresh-session step. `harden`: `/spike-loop:poc-harden`. `stop`: `/spike-loop:poc-checkpoint stop`.
6. Do not commit.
